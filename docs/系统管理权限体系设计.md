# 系统管理权限体系设计

## 1. 目标

系统管理模块用于把平台账号、商户账号、门店成员账号、出资方账号统一纳入总部可配置、可审计、可隔离的权限体系。

本模块解决三个核心问题：

- 谁可以登录系统。
- 谁可以操作哪些功能。
- 谁可以看到哪些商户、门店、资产、配件、订单、分润数据。

权限体系采用三层模型：

- 角色：定义岗位身份。
- 权限：定义可执行的功能动作。
- 数据范围：定义可访问的数据边界。

## 2. 适用对象

- 平台管理员
- 平台财务
- 商户老板
- 店长
- 门店运营成员
- 维修人员
- 仓库/配件人员
- 出资方

## 3. 系统管理模块结构

建议总部后台新增一级菜单 `系统管理`，下设 7 个子模块：

1. 账号管理
2. 角色管理
3. 权限管理
4. 角色授权
5. 数据范围管理
6. 账号授权管理
7. 操作审计

第一期开发范围建议先覆盖：

1. 账号管理
2. 角色管理
3. 权限管理
4. 数据范围管理
5. 操作审计

第二期再补：

1. 角色授权
2. 账号授权管理

## 4. 模块说明

### 4.1 账号管理

负责管理登录账号本身。

功能：

- 创建账号
- 编辑账号基础信息
- 重置密码
- 启用/停用账号
- 查看账号绑定角色
- 查看账号所属商户/门店/出资方
- 查看最后登录时间

账号主体类型：

- 平台账号
- 商户账号
- 出资方账号
- 消费者账号

关键字段：

- 账号 ID
- 账号类型
- 用户名
- 手机号
- 显示名称
- 所属商户
- 默认门店
- 所属出资方
- 状态
- 最后登录时间

### 4.2 角色管理

负责管理岗位角色。

第一期内置角色建议：

- PLATFORM_ADMIN
- FINANCE
- MERCHANT_OWNER
- STORE_MANAGER
- STORE_OPERATOR
- STORE_STAFF
- MAINTENANCE_STAFF
- WAREHOUSE_STAFF
- INVESTOR
- CONSUMER

关键字段：

- 角色编码
- 角色名称
- 角色作用域
- 状态
- 默认权限数
- 适用对象说明

### 4.3 权限管理

负责管理细粒度权限点。

权限命名建议采用 `模块.动作` 形式，例如：

- merchant.read
- merchant.write
- store.read
- store.write
- order.read
- order.operate
- asset.read
- asset.operate
- inventory.read
- inventory.operate
- maintenance.read
- maintenance.operate
- settlement.read
- settlement.write
- system.admin

后续建议新增的系统管理权限：

- auth.account.read
- auth.account.write
- auth.role.read
- auth.role.write
- auth.permission.read
- auth.scope.read
- auth.scope.write
- auth.audit.read

### 4.4 角色授权

负责把权限点分配给角色，形成角色默认权限包。

说明：

- 角色授权是默认模板。
- 修改角色授权会影响所有绑定该角色的账号。
- 敏感角色变更必须保留审计。

### 4.5 数据范围管理

负责限制账号可访问的数据边界。

第一期重点控制门店范围，因为订单、资产、配件、维修、分润均以门店为核心隔离维度。

范围类型：

- PLATFORM_ALL：全平台
- ALL_MERCHANT_STORES：某商户全部门店
- MULTI_STORE：某商户指定多个门店
- SINGLE_STORE：某商户单个门店
- INVESTOR_SELF：仅本人名下资产与收益

第一期落地方式：

- 平台管理员默认全平台
- 商户老板默认 `ALL_MERCHANT_STORES`
- 店长、运营、维修、仓库成员默认 `SINGLE_STORE` 或多门店组合
- 出资方默认 `INVESTOR_SELF`

### 4.6 账号授权管理

负责给具体账号做差异化授权。

适用场景：

- 店长不能看分润
- 维修主管可跨两个门店
- 仓库人员可看配件但不能看订单

当前已先落地租赁订单创建权限：

- 权限编码：`order.create`
- 默认状态：商户和门店账号均不默认授予
- 授权方式：平台管理员在账号管理中按账号开启或关闭
- 生效范围：只能为账号授权门店内的上架商品创建订单
- 结算与账单：订单创建成功后自动生成整单账单计划
- 权限隔离：`order.create` 与订单查看、履约操作权限相互独立

其他账号级差异化权限继续按第二期范围逐步实现。

### 4.7 操作审计

负责记录系统管理相关敏感操作。

必须审计的动作：

- 创建账号
- 修改账号状态
- 重置密码
- 绑定/变更角色
- 调整门店范围
- 修改角色权限
- 查看敏感账号信息

## 5. 角色与默认权限建议

### 5.1 平台管理员

- 数据范围：全平台
- 默认权限：全部权限

### 5.2 财务

- 数据范围：全平台
- 默认权限：订单查看、账单查看、支付查看、结算查看、出资方收益查看、审计查看

### 5.3 商户老板

- 数据范围：所属商户全部门店
- 默认权限：门店查看、订单查看、资产查看、配件查看、维修查看、结算查看、员工账号管理

### 5.4 店长

- 数据范围：授权门店
- 默认权限：订单查看、订单操作、资产查看、资产操作、配件查看、维修查看、维修登记

### 5.5 门店运营成员

- 数据范围：授权门店
- 默认权限：订单查看、核销、取车、换车、还车、资产查看

### 5.6 维修人员

- 数据范围：授权门店
- 默认权限：资产查看、配件查看、配件操作、维修查看、维修登记

### 5.7 仓库人员

- 数据范围：授权门店
- 默认权限：配件查看、配件入库、配件调整、库存流水查看

### 5.8 出资方

- 数据范围：本人名下资产与收益
- 默认权限：资产查看、收益查看、维修记录查看、租赁记录查看

## 6. 数据隔离规则

### 6.1 商户体系账号

商户体系账号必须同时满足以下条件：

- 账号属于某个商户
- 账号绑定至少一个角色
- 账号绑定明确的数据范围

### 6.2 资产

资产查询必须至少按以下条件之一过滤：

- 当前账号为平台管理员
- 当前账号的门店范围命中资产当前所在门店
- 当前账号为出资方且资产属于本人名下

### 6.3 配件与维修

配件库存、库存流水、维修记录按门店范围控制。

规则：

- 门店成员只能看自己授权门店的数据
- 不能跨商户看库存
- 不能跨门店消耗库存

### 6.4 订单与账单

订单、账单、逾期、履约记录必须按门店范围控制。

### 6.5 分润与收益

商户成员默认只能查看自己门店相关收益。

出资方默认只能查看自己名下资产产生的收益。

## 8. 第一期开发边界

第一期先不做的内容：

- 自定义拖拽式权限编排
- 账号级权限覆盖规则引擎
- 多级审批流
- 复杂的字段级脱敏授权

第一期只要求做到：

- 总部可创建和停用账号
- 总部可给账号分配角色
- 总部可给账号配置门店范围
- 商户和门店成员登录后只能看到自己权限范围内的数据
- 所有关键变更有审计记录

## 9. 与现有代码的对应关系

当前系统已经具备以下基础：

- 账号表：`sys_account`
- 角色表：`auth_role`
- 权限表：`auth_permission`
- 角色权限表：`auth_role_permission`
- 账号门店范围表：`auth_account_store_scope`
- 登录鉴权：`auth` 模块
- 门店范围校验：`AuthorizationService.requireStoreAccess`

当前缺口主要是：

- 缺系统管理后台菜单与页面
- 缺角色、权限、账号的总部可视化管理能力
- 缺角色和数据范围的统一配置入口
- 缺系统管理专属权限点

已补充的账号级授权基础：

- `auth_account_permission` 保存账号直接获得的权限
- 登录态有效权限由角色权限与账号直接权限合并计算
- 当前仅开放 `order.create` 作为可直接分配权限
